# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## State of the project

XilaOS is a hobby operating system. Its first version was built on 2026-11-18 and 2026-11-19 and published as XilaOS 0.1; development resumed on 2026-11-23, with no schedule. What follows is the briefing the work is done from: keep it in step with the code. Documentation, code, comments and everything the system shows on screen are in English.

Boot, screen, keyboard, shell, serial port, preemptive kernel tasks, kernel memory, the city view, SQL (system views and stored tables, kept on a virtio disk) and LISTEN / NOTIFY work in QEMU. On 2026-11-18 the author started their Lenovo T430 from the USB stick, installed XilaOS on its disk with `install` and started from the disk, without a problem; the graphics chip, the network card, the remote prompt, the web pages and the start from the network were then tried there too. On 2026-11-27 it was started from the network with the kernel of that day and its disk taken again whole (`install from`, `install n yes`): the volume there was made in version 3 of the format. The same day constraints, indexes, `ALTER TABLE`, joins, `disk check`, names and TLS were tried there through its prompt over the network, with the statements of `tools/check.py`, and the companion with a real model, asked by a program: first through a relay on the development machine that held the key, then with the key kept on the T430 (the table of `docs/13-status-and-roadmap.md` says what was tried). The system installed there at the end of that day is the one of commit `fa65ed4`: the key was still there after the restart, `companions` was refused to the network prompt, and the companion's answers came with their accents once `talk` was emptied (the rows an older system had written held `?` for accents, and the model, which is sent its last answers, imitated them: when a model writes something odd, look at what `talk` shows it before looking at the code). A trial of that kind is worth writing against QEMU first: that is how a fault no check had met was found (`now` unknown in an `on` program). It is the only real hardware XilaOS has run on. That machine has no serial port in use: what happens there is known from what the author reads on its screen.

The project is under the GNU AGPL (version 3 or later).

## Commands

```sh
cargo test -p xila-core -p xila-db -p xila-tls   # unit tests of the logic, the storage engine and TLS, on the host
cargo test -p xila-core ui::tests::menu      # one test, or a group, by name
tools/build.sh                               # kernel -> build/esp/EFI/BOOT/BOOTX64.EFI
python3 tools/check.py                       # the whole system in QEMU (after build.sh)
tools/run.sh                                 # build and open QEMU with a window; serial port on the terminal
tools/usb.sh                                 # build, then the image of a USB stick: build/xilaos-usb.img
python3 tools/netboot.py                     # serve the kernel to a PC that starts from its network cable (--check tries it alone)
python3 tools/remote.py ADDRESS CODE [cmd]   # the prompt of a running machine, over the network (after `remote on` there)
python3 tools/xq.py cmd:about type:help key:ret peek shot:build/shots/x   # drive it by hand
python3 tools/docs.py                        # the documentation as one PDF: docs/xilaos.pdf (needs pandoc and weasyprint)
```

- The kernel target is `x86_64-unknown-uefi`. The Rust on this machine comes from Homebrew and has no such target, so `tools/build.sh` compiles in the Docker image `xilaos-build` (it creates the image if missing). With rustup and the target installed it uses the local cargo instead.
- A file written on the host can take a moment to appear in the container; `build.sh` runs `sync` first. If a build fails on a truncated file, build again.
- `cargo build` for the whole workspace on the host does not work (the kernel only builds for UEFI); always name the package.
- `tls/` rests on libraries from the registry (the only outside code): the first build and the first test fetch them. `build.sh` keeps them in `target/docker-registry` for Docker. `.cargo/config.toml` tells four of them to use their plain code for the kernel's target, which has no vector instructions: a new library that picks such instructions while running fails to compile there with an LLVM error, and needs its own line.
- QEMU needs the UEFI firmware `edk2-x86_64-code.fd` that Homebrew's QEMU ships; `XILA_FIRMWARE` overrides the path.

## Testing by driving the system

The serial port carries the same shell as the screen, and that is how changes are verified. `tools/xq.py` (`Xila` class) starts QEMU without a window, sends commands on the serial port, presses keys through the QEMU monitor and takes screenshots.

- Every serial command ends with a status line, `#ok` or `#error`, then the prompt. Tables are sent as `#table name<TAB>columns`, tab separated rows, `#end`.
- `peek` returns the characters currently on the screen, one line per row. The serial task brings the grid up to date before each command, so `peek` right after a command shows its effect. Use it to assert what the user sees; use `shot` and look at the PNG when colors or drawing matter.
- QEMU key names are positions on a US keyboard, which is the layout the system starts with (the author's choice; `keymap fr` gives AZERTY).
- Events a serial session listens to arrive as `#event channel<TAB>text` lines before the status line of its next command; `Xila.cmd` moves them to `Xila.events`.
- While a block of the language is open on the serial port, each line is answered by `#more` then `#ok`; `Xila.more` says so. Nothing runs until the last `end`.
- The database's disk is a file given to QEMU as a virtio disk: `Xila(disk=path)`, with `blank_disk(path)` to start from an empty one. `Xila(sata=path)` gives a SATA disk instead, made with `partitioned_disk(path, megabytes, partitions)`; `cpu="max"` picks a processor with 1 GB pages. Without either the tables live in memory. The disk QEMU boots from is itself a SATA disk without a XilaOS partition. `Xila(stick=image)` starts from the image of a USB stick instead (`tools/usb.sh` makes it), which the kernel cannot see, as on a real machine; `Xila(bare=True)` starts from whatever the other disks hold, as a machine does once XilaOS is installed. QEMU's firmware keeps its settings in a file `NvVars` that it writes itself in the first start-up partition it finds: a start-up partition that went through a start of QEMU holds that file besides the kernel. `Xila(more=[...])` passes more arguments to QEMU. To see the interface at another size of screen, change `grid::DESIGNED` for a build (1360x768 is close to the T430's panel); not 1366x768, which QEMU's display rounds to 1360 while the firmware still says 1366, so the picture comes out sheared there and only there. `Xila.cut()` kills the machine as a power cut would. `tools/run.sh` uses `build/data.img` (virtio) and keeps it between runs.
- The processor QEMU imitates by default has no RDRAND, so nothing is asked through TLS there: `Xila(cpu="max")` for anything `https://`. QEMU's small network leads to the Internet when the host is connected; a check that needs it must be skipped when it is not (`online` in `tools/check.py`). A real server may also stay silent by its own choice (www.microsoft.com does, some of the time, to a question with no `User-Agent`): try the same from the host with the `meet` example before looking for a fault here.
- The SATA driver has only run on QEMU's controller and on the T430's. When changing it, keep to what the AHCI specification says rather than to what QEMU accepts.
- Times measured in QEMU on this Mac depend on how busy the virtual processor is: when the system idles they are three to four times longer than when a `spin` task runs. Compare like with like. QEMU does not imitate the slowness of real screen memory, so what write combining gains can only be measured on a real machine.
- Add a check to `tools/check.py` for every behavior that is added.

## Architecture

Four crates in one workspace:

- **`db/` (`xila-db`)** is the storage engine: tables of typed records, changed in transactions. `no_std` with `alloc`; with the `rsa` library inside `tls/`, it is the only code under `core/` that allocates. It knows nothing of SQL. Column 0 of every table is `id`, given by the engine. A column may ask something of its values (`Rule`, given to `create_with`): the engine itself holds `not_null` and `unique` in `insert` and `update_each_ids` (`Error::Missing`, `Error::Twice`; `unique` reads the table, there is no index, and looks at the table as the statement leaves it), and only keeps the value by default and the texts of the checks, which are for whoever makes the rows. A column may also have an index (`index.rs`, `Database::index`, `unindex`; a unique column gets one with its table): one more tree, from the *mark* of a value (a number as it is, sign bit turned; FNV-1a of a text, so one text is found and not a span of them) to the ids of the rows that have it, in the record up to 32 of them and in a tree of their own beyond. `insert`, `update_each_ids` and `delete_ids` keep it in step inside the same transaction, `tables_of` marks its pages at open, `remove` frees them, and `verify` reads it against its table: anything new that writes rows must do the same, and the test of random changes (`many_changes_at_random_match_a_plain_map`, both columns indexed) and the power cuts of `a_power_cut_while_indexed_rows_change...` must keep passing. `scan_by` reads rows through an index, and reads the table instead when the rows are more than half as many as the table has leaves, since each may cost a page reached from the root: what it gives is rows that may have the value, and maybe all of them, so whoever asks looks at each. All of it is in the catalog after what version 1 of the format had, and only for a table that asks something: so a volume of version 1 or 2 is read as it is, and its headers say 3 from the first commit on (`store::VERSION`, `OLDEST`). A change to what the catalog holds must keep that true or raise the version, and `a_volume_of_an_older_version_is_read_and_is_of_this_one_once_it_is_written` passing. It has three layers, and `index.rs` over the last two. `disk.rs`: a `Volume` of 4 KB pages over a `Disk` (the kernel's virtio disk, or `Memory`); a mirror would go here. `store.rs`: copy-on-write pages, a checksum in each, two header pages written in turn; a commit is the write of one header, and the free pages are found again at open by walking the trees. `tree.rs`: B-trees from a number to bytes; one per table (id to record) and one for the catalog. `lib.rs`: tables, records, and transactions (`commit` reports the changes and returns once they are safe on the volume, `rollback` drops them). `Database::verify` (`disk check`) forgets the pages kept in memory first, so that it reads the volume: a check of what memory holds says nothing of the disk. `testing.rs` has a disk whose power can be cut at any write: any change to `store.rs` or `tree.rs` must keep those tests passing, and a new kind of write needs a scenario there.
- **`tls/` (`xila-tls`)** is TLS 1.3 for the side that calls, and the only crate with outside code. The protocol is written here (`client.rs`: the handshake and the records; `keys.rs`: the keys of each step and the sealing); the arithmetic (X25519, ChaCha20-Poly1305, SHA-2, ECDSA on P-256 and P-384, RSA) comes from RustCrypto and dalek, and the checking of a chain of certificates from `rustls-webpki` with the authorities of `webpki-roots` (`check.rs`). Never write those again here, and never add a way to trust an authority while running. `Client` is a machine fed with bytes like `tcp.rs` (`wants`, `input`, `output`, `write`, `read`, `state`), 37 KB of buffers of its own, no heap except inside `rsa`. One key exchange, one cipher: a server that wants another gets `Error::NoCommon`. Its tests play the server (`tests.rs`) with the made-up certificates of `tls/fixtures` (`make.sh` made them; they are good for a hundred years from 2026-11-26, and `check::tests::NOW` must stay inside that time); `cargo run -p xila-tls --example meet -- NAME [--at ADDRESS:PORT] [--root FILE.der]` tries it from the host against any server, which is how `tools/check.py` sets it against OpenSSL.
- **`core/` (`xila-core`)** is all the logic, with no hardware and no heap of its own (only `System::db` allocates): fixed size buffers only, `no_std` outside tests. The kernel feeds it scancodes, serial bytes and timer ticks and copies the resulting character grid to the screen. Everything that can be decided without touching the machine belongs here, with unit tests.
- **`kernel/` (`xila-kernel`)** is a UEFI application. `uefi.rs` holds hand-written bindings for the few firmware calls it needs; it picks the graphics mode (`grid::choose`: the panel's own size if the panel tells it, else 1280x800, which is what QEMU gives and what every check assumes, else the sharpest; the T430's firmware does not offer 1280x800), reads the file the firmware started (the kernel itself, kept in memory for `install`: the kernel has no USB driver, so only the firmware can read a stick, and only before the boot services are left), reads the memory map and leaves the boot services. `arch.rs` then installs its own GDT and IDT, the interrupt controllers, a 100 Hz timer and the PS/2 keyboard. `task.rs` is the scheduler. `arch::map_memory` replaces the firmware's page tables by an identity map of the kernel's own (1 GB pages, or 2 MB when the processor has none), in which the pages of the screen, and only those, are write combining (`arch::combines` reads it back from the tables in use). `arch::micros` is a fine clock, the processor's counter measured against the timer. The kernel is compiled without vector instructions (the Rust UEFI target turns them off): no SSE intrinsics. `pci.rs` scans the bus. `virtio.rs` (legacy interface over I/O ports) and `ahci.rs` (SATA) are the disk drivers: one request at a time, polled, with timeouts in timer ticks, so interrupts must be on. `disk.rs` picks the disk at boot and opens the database on it: a virtio disk whole, or on a SATA disk only the GPT partition of XilaOS's type (`xila_core::gpt`, never anything else on a real disk, except by `install n yes`). A disk that is refused is kept in `System::spare` for the `disk erase yes` command. `disk::Disks` keeps every SATA disk for `install`; a `Sata` can be cloned, so the database and the installer may each hold a hand on the same disk, which is safe only because both work under the lock of `SHARED`. `main.rs` holds the tasks: the interface (keyboard, redraw) and the serial shell.

How the pieces fit:

- **Text** is bytes in the character set of the V2_OS font (ASCII below 0x80), not UTF-8, so it is `&[u8]` everywhere (`b"..."` literals, `FixedStr<N>` buffers). Above 0x80 the font has the accented letters of code page 850 where V2_OS kept them, among drawings of its own; `core/src/chars.rs` is the one table between them and Unicode (`shown`: what the font shows for a character, its own letter, the nearest thing, or `?`; `unicode`, `utf8`, `read`). Whatever takes text in from outside or sends it out goes through it: `json::text` and `json::Writer` for the companion (`json::inner` and `Writer::json` for JSON held in a text, which stays UTF-8 until its own texts are read), `web::Page::text` for browsers. The serial port and the QR codes still send `?`. A place that cleans a text for the screen must keep bytes above 0x7f: `companion::tell` once turned them into spaces.
- **Display**: `ui::Ui` owns a `Grid` of 80 columns by up to 50 rows of `Cell`s. A cell stores a character, two color *roles* (`theme::role`) and effect bits (`grid::fx`: big logo letters, rounded bar ends, pulsing cursor). `Ui::render` rewrites the whole grid from the state on every change; the grid records which cells really changed. Nothing is drawn in the memory of the screen: `fb::Screen::compose` draws the changed cells (16x16 pixels each at 1280x800) into a picture in ordinary memory, and `show` copies the spans that changed to the screen with `rep movs`. Colors come from `theme::THEMES`, so a theme change is only a redraw. What moves by itself (the city, the cursor) advances once every `shell::FRAME_TICKS` ticks, 25 pictures per second; what the user changes is shown at the next tick. The `display` command reports the measured times (`System::display`), and a boot log line times a whole screen with and without write combining.
- **City** (`core/src/city.rs`): `scene(&System)` turns the system state into six plots of blocks with heights; `City` animates and draws them, isometric, into a 640x176 picture of `u32` colors. The kernel owns the picture, redraws it 25 times per second (the speeds in `City::step` are tuned for that) and puts it over rows `BODY_TOP..BODY_TOP + CITY_ROWS` of the overview screen (`fb::Screen::blit`); `compose` skips those rows. The `city` command returns the same scene as a table. To look at the drawing without booting: `cargo run -p xila-core --example city -- day > city.ppm`. Only real state is shown; add a block by adding to `scene`.
- **SQL** (`core/src/sql.rs`, `core/src/expr.rs`, `core/src/change.rs`, `core/src/catalog.rs`): `sql::select(&dyn Source, query)` parses and runs a SELECT and returns a `shell::Table`. Everything that stands for a value (`amount * 2`, `n > 3 or tag is null`, `round(x, 2)`) is an `expr::Expr`: read once into a small tree in a fixed array, then worked out per row with `eval` or `holds`. Its rules (calculator division, exact numbers, errors rather than wrong results) are at the top of `expr.rs`; the house language will use the same expressions. In the list of a SELECT an item may be made of functions over the rows (`sum(a) / count(*)`): `expr::parse_item` keeps each one in an `Aggregates`, and the item is then an expression over a row of their results. A `Source` describes a table by name (`Schema`) and scans its rows; `System` is the only one. `Expr::bounds` tells what a condition says of the first column, and `Source::scan_among` lets a stored table go straight to those rows by their `id` (`Database::scan_ids`, `tree::range`); `sql::way` decides for each table of a SELECT: by the id when the conditions bound it, else by the first column that has an index (`Schema::indexed`) and that they bound (`bounds` for a whole number, `Expr::pins_beside` for the one value of a text or a decimal), through `Source::scan_by`, else the whole table; every row reached is still given to the conditions, which is what makes a wrong guess harmless; `change.rs` does the same for UPDATE and DELETE, and `disk` counts the pages read (`Storage::looked`). A SELECT joins two tables at most (`from a join b on ...`, `left join`): the row a condition is worked out for is then the two rows side by side, the second table's columns from `expr::JOINED` on (`expr::Names::column` finds a name in either table), and the second table is read once for each row of the first, through `scan_among` with what `Expr::bounds_beside` says of its id, or through `scan_by` when that says nothing and one of its columns has an index the condition pins. The first table is read by `Source::scan_apart`, leaf by leaf, because a plain scan of the engine cannot be nested (`Error::Busy`). It has two kinds of tables: views of live state (`catalog::TABLES`: `tasks`, `settings`, `memory`, `city`...), numbered first, and the stored tables of `System::db`, numbered after them. `change::change(db, statement, report)` runs CREATE TABLE, DROP TABLE, INSERT, UPDATE and DELETE: one statement is one transaction, committed on success and rolled back on any error, and `report` is called for each changed row after the commit. CREATE TABLE reads what the columns ask (`not null`, `unique`, `default CONSTANT`, `check (condition)`, four checks of 60 characters at most, so that the answer that refuses a row can quote one whole); INSERT gives the value by default to a column it is not given, and INSERT and UPDATE work out the checks for every row they write (`change::Checks`, read once per statement with `Expr::fails`: a check that cannot be known lets the row in). Anything new that writes rows of the user's tables without going through `change.rs` skips defaults and checks: say so, or go through it. `show table NAME` (`change::written`) writes the statements that would make a table and its indexes; the `rules` and `index` columns of the view `columns` say the same per column. `CREATE INDEX ON t (c)` and `DROP INDEX ON t (c)` (`change::index`): no name, one column, a statement of its own as CREATE TABLE is; UPDATE and DELETE do not go through indexes yet (`change::among` knows the id only). `ALTER TABLE` (`change::alter`) adds, drops and renames columns, renames a table and changes what a column asks, one change per statement, through the engine's `add_column`, `drop_column`, `rename`, `rename_column`, `set_not_null`, `set_default`, `set_unique`, `add_check` and `drop_check`: whatever is added is asked of the rows the table has first (the engine for a value that must be there or cannot be twice, `alter` itself for a check, which the engine does not read), a column a check names is neither dropped nor renamed, and who listens to the table hears `alter` once. `change::definition` reads a column for CREATE and for ALTER alike. `change::target` knows every statement that changes a table, which is what keeps the companion from those that hold it: a new statement goes there too. Reading and committing can fail (disk error, damaged page): `Source::scan` and `Database::commit` return the error and `change::engine_error` words it for the user. Values are `Null`, `Int`, `Dec(units, scale)` (exact decimal) or `Text` (48 bytes at most). To add a system view: a `TableDef` in `catalog::TABLES` and an arm in `scan`, whose numbers follow the order of `TABLES`. Results are capped by `TABLE_COLS` and `TABLE_ROWS`. The `data` plot of the city has room for nine blocks and there are nine views: a tenth will not show there.
- **Language** (`core/src/lang.rs`): XilaScript, what the prompt understands beyond one command. `shell::exec` gives every line to it: a line that opens a block (`if`, `while`, `for`, `program`) is collected in `System::blocks[session]` until its `end`, then run or stored; any other line is one statement. `let`, `say`, the blocks, `run` and `return` are run by `lang`; everything else falls through to `shell::command`, so every command is a statement. Lines are interpreted as read, with no compilation. Variables are per session (`System::vars`, `expr::Vars`) and expressions resolve a name as a column first, then a variable, which is how SQL sees them. Programs are rows of the stored table `programs` (name, line, text), read through `xila-db` directly because their lines are longer than the 48 characters a `Value` holds. A program that runs by itself (`on ...`, `every ...`) has its first line as line 0. `lang::background`, called by `Ui::tick`, runs them: `every` programs from `System::triggers` when their tick comes, `on` programs from the queue `Events` fills for programs (`take_happened`). They run as the pseudo session `events::BACKGROUND`, with fresh variables, and write to the log screen. Inside any program, `Style::Done` lines (a command saying it succeeded) are not shown.
- **Install** (`core/src/gpt.rs`, `fat.rs`, `install.rs`): `install n yes` takes a whole disk. `gpt::Layout` is the partition table (a 100 MB start-up partition named `XilaOS start`, the rest for the tables) and `gpt::describe` tells what a disk holds. `fat::Fat` is the start-up partition a firmware reads, FAT32 with the one file `EFI\BOOT\BOOTX64.EFI`: it can tell what any of its sectors holds, so nothing is built in memory; it is only ever made new and whole, never read or changed, and is not a file system of XilaOS. `install::whole` and `install::system` do the writes through the `Sectors` trait and read everything back before they return; `kernel/src/disk.rs` gives them a `Sata`, drops any hand the database had on the old partitions first, and opens the database on the new one. `install system` rewrites the start-up partition only. The image of the USB stick is made by the same code on the host (`core/examples/usb.rs`), so starting QEMU from it checks that code with a real firmware. Whatever changes here must keep the three independent readers happy: the test reader in `fat.rs`, the Python one in `tools/check.py`, and `fsck_msdos`.
- **Graphics chip** (`core/src/intel.rs`, `kernel/src/chip.rs`): the Intel chip of the T430 (HD Graphics 4000) and its siblings of 2011 and 2012. `display chip` says what the firmware set up (pipe, plane, panel fitter, panel, brightness, what graphics memory is mapped behind the screen) and `display registers` lists the 32 registers read; both only read, and the author's T430 (a 1600x900 panel) confirmed the reading on 2026-11-18. Two things write to the chip. `intel::Flip` puts a second picture in the graphics memory behind the screen and the kernel's `chip::Flipper` and `fb::Screen` show the two in turn, changed by the chip between two sweeps (`grid::Changes` keeps what each picture still needs); it is on from the start where the chip allows it, which the author's T430 proved (also from the start, with the rhythm below, on 2026-11-18), and `display flip off` and `on` switch it. The screen then gives the rhythm of what moves by itself (`ui::Rhythm`, from the chip's count of sweeps: a picture every two sweeps at 60 Hz, so 30 pictures per second on the T430 against 25 by the timer in QEMU). `intel::Light` sets the brightness of the panel (`display brightness 60`). `display flip try` does the same with two pictures in ordinary memory, on any machine: that is how `tools/check.py` exercises the logic, since QEMU has no such chip. All of the reading and decoding is in `core/`, behind the `intel::Chip` trait (read a register, tell the time); the kernel's `chip.rs` finds the card on the PCI bus and gives the trait real registers. QEMU imitates no such chip, so none of this runs in `tools/check.py` beyond "not known": the unit tests use a chip made up from the register description, and on the real machine the table checks itself (the row `the firmware's screen` says whether the plane the chip shows is the framebuffer the firmware gave the kernel). Register addresses come from Linux's `i915_reg.h` (v4.9): check them there, not from memory, before adding one. A device's registers can only be read when they lie below `arch::mapped()`.
- **Codes** (`core/src/qr.rs`): `qr command` runs a command, keeps what it says (`shell::Note`, an `Out`: lines, and tables with tabs between cells) and shows it as a QR code, which is how text leaves the T430: the author reads it with a phone and pastes it. The command's kernel answer, if any, is part of the text, which is why the code is made in `shell::served` and not in the command. `System::code` being `Some` puts the interface in a mode of its own: `Ui` blanks the body and any key puts the code away; the kernel paints the code (`qr::paint`) over the rows below the title bar, as it does for the city. `tools/qr.swift` reads a code from a screenshot with macOS's own reader and `tools/check.py` compares; it skips those checks where there is no `swift`.
- **The companion** (`core/src/companion.rs`, `core/src/json.rs`, `docs/14-the-companion.md`): `ask QUESTION` sends a question to a model of the Internet (chat completions, as OpenRouter speaks them) and shows its answer; the model reads the tables, runs lines at the prompt and keeps facts. No network in `companion.rs`: `ask` writes the question in the stored table `talk` and sets `System::companion` to `Stage::Calling`; `request` writes the JSON to send (what the model is told, `TOLD`; the last six turns of `talk`; the last twenty rows of `remembered`; the three tools of `TOOLS`, named again in `TOOL`); `heard` takes the answer, keeps what was said, does what the model asked for and either stays `Calling` or ends with an `Outcome`. `select` goes to `sql::select(&System)`, which cannot change anything. `run` goes to `companion::act`: one line through `lang::line` as the session `events::BACKGROUND`, with `System::acting` set, then a row of the stored table `acts` (turn, at, command, went), whatever came of it. `remember` adds a row to `remembered` (at, text). **What holds the companion is three things, and each must stay whole:** the record (`acts`); `companion off` (`companion::switch`, kept between starts; `companion on` is refused to the companion itself, not to the prompt over the network nor to a program of the user's); and what is refused while `System::acting` is set: `shell::at_the_machine` (`install`, `disk erase`, `remote on`, `web on`: true only for the screen and the serial port, so also false for the network session and for a program that runs by itself, which either could have written), `key`, `reboot`, `ask`, `companion on`, blocks (`lang::opens`), a request left for the kernel (taken back in `act`), and any change to the tables of `companion::held_by` (`programs`, `acts`, `companions`: checked in `shell::change` through `change::target`, and through `change::becomes` for a table that would be given one of those names; and `drop program`). A new command that takes a disk, opens the machine, shows or changes a key, or writes programs by another way than `shell::change` needs its own refusal, a line in `what_is_not_its_own_is_refused_to_it` or `what_holds_it_is_not_its_own_to_change`, and a row in the table of `docs/14-the-companion.md`. It may still drop or empty any table of the user's: the docs say so, keep saying so until access rights exist. The kernel's `companion` in `main.rs` carries the bytes, one pass per tick of the interface task (name, TLS client, `Ask`), so nothing blocks; `companion::tell` gives the outcome to the session that asked (`Ui::tick` for the screen; the serial task waits for it before its status line). `talk` rows are (turn, who, text): `you`, `xila`, `more` (the rest of a long answer), `select`, `run`, `remember`, `result`; texts up to 900 bytes, of which SQL shows 48 (`sql::row_from` turns line breaks and tabs into spaces). Who it is: the first row of the stored table `companions` (name, place, model, key, character), made at the first question. The key (`secrets.rs`) is only sent to an `https://` place. `json.rs` has no tree: `Writer` into a buffer, `get`/`item`/`path` give slices of the text, `text` decodes one. In `tools/check.py` the model is a made-up one on the host (`Served.model`, told what to say through `model_says`: `said`, `queries`, `runs`, `facts`), reached by plain HTTP; the refusals are checked with it, since a real model declines to try; the real one is asked when `OPENROUTER_API_KEY` or `.env.local` gives a key and the host is online.
- **What happens to the machine** (`core/src/watch.rs`): `watch::look`, called by `Ui::tick` after `lang::background`, compares the state of the system with what it saw a second before (`System::watch`) and says what has become true on five channels, through `Events::notify`: `start`, `network` (cable, address, a door closed by wrong codes), `disk` (almost full, a write failed, a damaged page: `System::damaged`, a cell counted where tables are read), `tasks` (a task with nine tenths of the processor for ten seconds), `memory`. Each once; what lasts less than a second is not seen. A new state to tell of: a field of `Watch`, a comparison in `look`, a row in the table of `docs/04-sql.md`. Programs hear them with `on notify CHANNEL`, and `ask` in a program is how the companion reacts: `companion::ask_later` puts the question in a queue of eight, `companion::next` (from `Ui::tick`) asks it when nothing else is being answered, and the conversation is written on the companion's screen under the program's name (`System::firing`, set by `lang::fire`).
- **Keys to services** (`core/src/secrets.rs`; `keys.rs` is the keyboard): `key set NAME KEY`, `key`, `key forget NAME`. Keys are rows of the stored table `kept_keys`, which only `secrets.rs` reads (`secrets::get` for whoever is about to use one). `catalog::kept_apart` keeps that table out of everything that goes through SQL: `Source::schema`, the `tables` and `columns` views, `change::stored` and `create`, the city. Anything new that walks `db.tables()` must skip it too; a unit test (`keys_are_kept_and_never_shown`) runs commands and looks for the key and the table's name in what they say: add new commands that list things to it. `shell::typed` is a line as a screen may show it (stars for the key), and `Ui` does not keep such a line in the history. Not a vault: the disk is in clear, and the serial port echoes the line. `key set` is refused to the line typed over the network, not to a program written there (the docs say so), and the key goes to whatever `https://` place the row of `companions` names: that table is changed at the machine only (`shell::change`, with `at_the_machine`), which must stay true of any new way to write it.
- **Kept settings** (`core/src/settings.rs`): keyboard layout, theme, mood, brightness, the choice of writing the screen directly and the companion being off are rows of the stored table `kept_settings`. `settings::keep`, called at every tick by `Ui::tick`, writes what differs from `System::kept`, so nothing else has to ask; `settings::load` puts them in use at start (the kernel calls it right after the database is opened, and applies the two that need the chip). Whatever replaces `System::db` by a database on a disk sets `System::kept = None`, so that the settings in use follow. A new setting to keep is a field of `settings::Kept`, a row in `rows` and an arm in `take`.
- **Clock** (`core/src/clock.rs`): the time is what the machine's battery clock says, as it is (no time zone). The kernel reads it at start and once a minute (`arch::clock_read`) into `System::clock`, and `System::now()` adds what the timer has counted since: seconds since the year 2000. `time` shows it; in any expression the names `now` and `today` are texts that sort (`expr::Vars::clock`, set by `shell::exec` for each line and by `lang::fire` for a program that runs by itself); `every day at 8:00` programs are kept among the `every` ones with the second of their next run. In QEMU the clock is the host's in UTC; `Xila(more=["-rtc", "base=2026-03-04T23:59:45"])` sets it for a check.
- **The prompt over the network** (`core/src/remote.rs`, `tools/remote.py`): a third session, `events::NETWORK`, beside the screen and the serial port. Closed at every start; `remote on` (refused from the network session itself) opens it with a code drawn from `System::chance`, which the kernel stirs in `observe`. A UDP message to port 4000 is `CODE NUMBER line`; `Remote::asked` says what to do with it (nothing, run it, or send the last answer again for a repeated number), and the interface task in `main.rs` runs the line exactly as the serial task does, into a `remote::Answer` (the serial prompt's text format, `#table`…`#end`, `#ok`/`#error`), sent back in parts. Only senders on the local network with the code are answered; twenty wrong codes close it; `install`, `disk erase`, `remote on`, `web on`, `ask`, `key set` and any change to the table `companions` are refused there. The title bar shows `remote: open`, then the address of who types there, on every screen (`Ui::bar`). Nothing is encrypted, and the docs say so: keep saying so until that changes. In QEMU the guest's port is reached through a forwarded host port: `Xila(net="e1000e", forward=port)` and `remote.Machine("127.0.0.1", code, port)`, whose `cmd` returns what `Xila.cmd` does.
- **TCP** (`core/src/tcp.rs`, in `Net::tcp`): the side that is called. A state machine with no hardware: `input` takes segments, `tick` the time, `output` hands out the next segment to send until it has none; `Net::receive`, `Net::tick` and `Net::speak` carry them (call `speak` after a program wrote). A program uses `listen(port)`, `accept(port)`, `read`, `write` (takes what fits: 4 KB unacknowledged at most), `close`, `alive`, `ended`. `connect(to, port, now)` calls another machine (`connected` says when it answered). Eight conversations, no out-of-order reassembly. Its tests play the other side (`Peer`). `core/src/ask.rs` asks one HTTP question over it (`Ask::start`, `step`); `net get PLACE` runs one to the end while the command is served (`get` in `main.rs`, which first finds the address when the place is a name). With `https://` the question goes through TLS: `get` makes a `xila_tls::Client` on the heap with 64 bytes from `arch::random` (RDRAND; without it nothing is asked, `Failed::NoChance`) and the date from `System::now()`, and `Ask::step` moves its bytes over TCP. A question (`ask::Question`) is `GET` or `POST`, lines of the asker's own (`Authorization: ...\r\n`) and bytes that go along, borrowed for the life of the `Ask`; `step` is given, at every call, the buffer where what was asked for is kept, without the lines before it nor the marks of chunks (`kept` bytes of it, `total` in all: what does not fit is counted and let go). It reads the three ways an answer ends (a said length, chunks, hanging up) and fails with `Failed::Cut` on one that was cut short; `patience` is the ticks of silence it waits through (five seconds unless set: a model that thinks needs more). `net get` and `net post` are how the calling side is tried: in QEMU the host is at 10.0.2.2, so a `http.server` on the host answers the guest.
- **The tables in a browser** (`core/src/web.rs`): `web on` opens port 80 with a code in the address, as `remote` does and with the same limits (local network, twenty wrong codes, nothing encrypted). `web::step`, called from the interface task, serves one browser at a time: reads the first line of what it asks, builds the whole page in `web::Page` (kept by the kernel) with `sql::select` on `&System`, which cannot change anything, and feeds it to TCP as room is made. Keep it read-only by construction: nothing a browser sends reaches `shell::exec`. In QEMU: `Xila(net="e1000e", web=port)` forwards a host TCP port; many connects at the very same moment are reset by QEMU's forwarding itself, not by XilaOS (seen in `build/net.pcap`).
- **A system from the network** (`core/src/tftp.rs`): `install from ADDRESS` (`Request::Fetch`) fetches `BOOTX64.EFI` by TFTP from a machine that serves it, which is what `tools/netboot.py` does; `fetch` in `main.rs` runs it to the end while the command is served, into pages kept for that, checks it has the shape of a system (`tftp::is_system`) and makes it the `system` that `install` writes. Nothing authenticates server or file, so every form of `install` stays refused to the network session. In QEMU: `Xila(net="e1000e", tftp=folder)` makes the folder's files available at 10.0.2.2.
- **Names** (`core/src/dns.rs`, in `Net::names`): the address of a machine known by its name. A state machine with no hardware: `Names::look(name, now, message)` answers from the eight names it keeps or says what question to send (again after one second, given up after three), `Names::answered` takes the UDP message that came back; `Net::name` carries both and is called again and again until it says something else than `Asking` (`named` in `main.rs` does that while `net name` or `net get NAME` is served). The server is the one DHCP named (option 6), or the one `net names ADDRESS[:PORT]` set by hand until `net restart`. IPv4 addresses only, names of 56 characters at most (`dns::NAME`, so that every line about a name fits the screen). In QEMU the network names 10.0.2.3, which passes questions on to the host's own name server; on this Mac that one is a VPN's and no answer comes back, so ask a server of the Internet (`net names 1.1.1.1`) or, as `tools/check.py` does, a small one on the host (`net names 10.0.2.2:PORT`).
- **Network** (`core/src/net.rs`, `kernel/src/e1000.rs`): `net::Net` (in `System::net`) is the stack with no hardware in it: `receive(frame, now, wire)` answers what any machine must (ARP for its address, a ping) and returns a UDP message addressed to a port of this machine; `tick` runs the DHCP client; `ping` and `message` send. It hands frames to a `net::Wire`, which the driver implements. `e1000::Nic` drives Intel cards of the e1000 family (QEMU's 82574 and 82540, the T430's 82579) through two rings of descriptors, polled by the interface task at every tick (`network` in `main.rs`), with no interrupt. The 82579 is shared with the machine's management engine and has ways of its own (`Nic::shared`: tell the engine a driver is there, wait before each register write, bits of the transmit side, K1 off when the link comes up, through the chip near the socket reached by `Nic::phy`); none of that runs in QEMU. **Change a register bit by bit; never write it whole unless every bit is known.** Five trials on the author's T430 received everything and sent nothing because `TCTL` was written whole: its unnamed top bits say how the card reads a frame out of its send memory, and at 0 frames went in and never came out. QEMU does not care, so no test here can catch that kind of mistake. What found it was measuring, not guessing: the card set up in several ways on one start, a frame sent to itself after each, and where the card said the frame was (`TDFH`/`TDFT`, still in `net registers`); that scaffolding was taken out of the driver once the cause was found, and is the thing to write again if a card ever refuses to send. The Linux sources this follows are best read whole: fetch them with `curl` from raw.githubusercontent.com (v4.9, `drivers/net/ethernet/intel/e1000e/`; iPXE's is `src/drivers/net/intel.c`) rather than through summaries. `net` shows card, cable, address and counters; `net ping`, `net restart` (reset and set up again) and `net registers` (the card's registers and what the driver knows, 32 rows, sized for one QR code) are kernel requests. To try it: `Xila(net="e1000e")` plugs the card into QEMU's own small network (address 10.0.2.15, gateway 10.0.2.2 which answers a ping) and keeps every frame in `build/net.pcap`, which `tools/check.py` reads back to check lengths and checksums by other code. There is no way to reach the guest from the host on that network except a forwarded port.
- **Events** (`core/src/events.rs`): LISTEN / NOTIFY. A session (`events::SCREEN` or `events::SERIAL`, set in `System::session` by whoever calls `shell::exec`) listens to channels; `shell::change` notifies the channel named after the table for each committed change. `Ui::tick` prints the screen's events in its terminal; the serial task writes its own before the status line.
- **Stack use**: tables and query buffers are large values on the stack (a SELECT takes about 50 KB, a running program 12 KB for its lines, a `for` 17 KB for its rows). Task stacks are 256 KB for that reason; keep it in mind before nesting such calls or growing those buffers. The flow that boots the kernel stays on the firmware's small stack and becomes the idle task.
- **Screens**: one `Term` (scrollback of rows) per virtual screen; `shell::SCREENS` names them in the order of their Alt+digit shortcut: the overview (the prompt, `Ui::editor`), the boot log (nothing to type) and the companion's (`Ui::chat`: Enter gives the line to `companion::ask` as `companion::HERE`, and `Ui::tick` writes the answer there through `ChatOut`, time and speaker before the first line).
- **Commands**: `shell::exec(&mut System, line, &mut dyn Out)`. `System` is the state commands may read and change. `Out` is where output goes: the terminal on screen (`ui.rs`) or the serial port (`kernel/src/main.rs`). List-like results go through `shell::Table`; rows added with `row_to` carry a command that runs when the user types the row number; each session follows the last numbered list it was shown (`System::last`).
- **Keyboard**: `keys::Decoder` turns set 1 scancodes into `KeyEvent`s for the `us` or `fr` layout. The `fr` layout has a dead key (circumflex, diaeresis): one scancode can then make two events, and `Decoder::rest` gives the second. `KeyEvent::digit` gives the digit printed on a top-row key regardless of layout, for Alt+digit.
- **Tasks** (`kernel/src/task.rs`): up to 8 kernel tasks with fixed 256 KB stacks, switched round-robin by the timer interrupt 100 times per second. The interrupt entry in `arch.rs` (assembly) saves the floating point state and all registers on the task's stack and calls `task::schedule`, which returns the stack of the next task; `int 0x30` (`arch::yield_now`) takes the same path. A task waits with `task::sleep(ticks)`. `schedule` is the only Rust that runs in interrupt context and it touches only the task table, which the other functions of `task.rs` access with interrupts off.
- **Memory** (`core/src/mem.rs`, `kernel/src/memory.rs`): `Pages` is a sorted list of free regions (first fit, merged on free), `Heap` cuts pages into power-of-two blocks. The kernel feeds them the free regions of the firmware memory map and exposes them as the global allocator, so `alloc` (`Box`, `Vec`, `String`) works in the kernel. `core/` itself stays without a heap. Every access runs with interrupts off.
- **Shared state**: `Ui`, `System` and the `Stage` (the screen, the city and its picture) live in `SHARED`, a `task::Mutex`. A task locks it, does its work, unlocks, then sleeps one tick. Devices are polled by tasks; their interrupts only acknowledge. The database, and so the disk, is only used by the task that holds this lock.
- **Kernel requests**: a command cannot call the kernel (it lives in `core/`). It leaves a `shell::Request` in `System`, and the task that ran it calls `serve` in `main.rs`. When the request has an answer (`display test`), the kernel leaves it in `System` and the task then calls `shell::served` (`Ui::served` for the screen), which shows it where the command was typed and returns false when the answer is a failure (any line of `Style::Error`): the command then ends with `#error`. `Request::Install` is the one request that draws while it is served: `install::Progress` tells how far it is and `Ui::progress` puts a bar on the last row. In the other direction the kernel copies what commands need into `System` first (`task::snapshot`).

The prompt's edit line holds 160 characters and slides under the prompt when it is longer than the row; a serial line holds 240.

To add a command: write the function in `shell.rs`, add it to the `match` in `command`, to `NAMES` (completion, kept sorted) and to `HELP_COMMANDS` (a unit test checks that every name is in a help and that lines fit in 80 columns), with a unit test, then a check in `tools/check.py`. Keep its help line short: `help c` must fit in one QR code, 2563 characters, which a check reads back whole (`qr help c`), and it holds 2550 since `alter table` (four other lines were shortened to make room for its own). A statement of the language goes in `lang.rs` instead, with its word in `shell::LANGUAGE` and its line in `HELP_LANGUAGE`.

## What must not be lost

- It is not a Unix. Do not reach for files, fork, POSIX or a Unix shell by default. The model is OS/400: a database at the core of the system, with data shared between applications under access control. SQL is its query language, and it has an internal LISTEN / NOTIFY.
- Programs are compiled for a virtual machine, not to native code: one made for XilaOS around the values and the tables of the database, and no other (decided on 2026-11-27; no WebAssembly). XilaScript, the language of the command prompt, with SQL built in, is interpreted today and is to be compiled for that machine, where a program runs as a job that holds nothing: the design is in `docs/13-status-and-roadmap.md` ("The virtual machine and the jobs"), not built. Its words are English.
- An application is an isolated zone with a public or private status and ACLs.
- The interface is in characters, with the V2_OS font, and is driven by the keyboard only.
- The system must keep working well in QEMU with the serial shell, so that an AI can run commands, develop and test.
